Documentación técnica

FerreSystem — Plataforma ERP-agnóstica multi-tenant

Motor genérico que conecta cualquier ERP con paneles web white-label sin reemplazar el sistema existente del cliente. Un adaptador por ERP, un JSON por entidad, N clientes sobre un mismo código.

Python 3.10+ HTML/CSS/JS Vanilla Firebase Hosting 6 adapters ERP 4 paneles white-label pytest · CI/CD

Inicio rápido

Desde cero hasta el primer despliegue de un cliente en 7 pasos.

1
Clonar el repositorio y crear el tenant Copiar tenants/ejemplo_tenant.json a tenants/{id}.json y completar todos los campos.
2
Configurar branding Crear branding/{id}/branding.json con color_primario, nombre_corto y logo.
3
Elegir o crear el adapter ERP Si el ERP ya tiene adapter (adapters/), apuntar con erp.tipo en el tenant. Si es nuevo, ver Agregar un ERP nuevo.
4
Crear proyecto Firebase Completar el bloque firebase en el tenant JSON con el project_id y la URL de hosting.
5
Ejecutar el setup python setup/setup_tenant.py {tenant_id} — valida la configuración y crea la estructura de carpetas en data/{id}/.
6
Correr el pipeline y validar pipeline/ACTUALIZAR_TODO.bat {tenant_id} descarga datos del ERP, genera los JSON y los valida contra el contrato.
7
Desplegar en Firebase firebase deploy --project {project_id} publica los paneles y los JSON en Firebase Hosting.

Capas del sistema

El principio rector es separar lo genérico (motor, paneles, validación) de lo específico de cada cliente. Lo específico vive siempre en datos, nunca en código.

tenants/{id}.json config del cliente — ERP, bodegas, branding, Firebase
│
▼
adapters/{erp}_adapter.py traduce el ERP a 4 entidades genéricas
│
▼
core/pipeline_runner.py orquesta: descarga → genera JSON → valida → rota token
│
▼
data/{id}/*.json salida estándar — misma forma para cualquier cliente
│
▼
paneles/*.html UI white-label — lee branding + datos, sin lógica de cliente

Multi-tenant

Un mismo despliegue del código sirve a N clientes. Lo que diferencia a cada cliente es exclusivamente:

  • tenants/{id}.json — configuración del cliente
  • branding/{id}/branding.json — colores y logo
  • El proyecto Firebase de destino (cada cliente tiene el suyo)

Seguridad

Credenciales del ERP

Nunca se guardan en texto plano. El campo password_enc (y equivalentes) almacena el valor cifrado con DPAPI del sistema operativo. Solo el proceso corriendo con las credenciales del usuario que cifró puede descifrarlas.

Rotación de token de acceso a datos

pipeline/rotar_token.py genera un subdirectorio de nombre aleatorio dentro de data/{id}/ y registra el token vigente en Firestore con reglas de seguridad. Los paneles construyen la URL de datos en tiempo de ejecución usando el token — URLs antiguas dejan de funcionar.

Aislamiento por tenant

Cada cliente tiene su propio proyecto Firebase. Nunca hay datos de un cliente en el espacio de almacenamiento de otro.

Qué nunca va en el repo

  • tenants/*.json reales (excluidos por .gitignore)
  • Claves de servicio Firebase (*.serviceAccount.json)
  • Tokens de acceso API de ERPs
  • Contraseñas cifradas con DPAPI
ℹ️ La regla #0 del proyecto: core/ y paneles/ nunca conocen el nombre, bodegas, ERP ni credenciales de ningún cliente. Si una función necesita ese dato, debe llegar por parámetro, nunca hardcodeado.

Agregar un ERP nuevo

1
Crear el archivo del adapter Nuevo archivo en adapters/{nombre}_adapter.py, clase que hereda de core.erp_adapter.ERPAdapter.
2
Implementar los 5 métodos abstractos get_productos(), get_stock(), get_ventas(desde, hasta), get_pedidos(), test_conexion(). Devolver siempre instancias de las dataclasses genéricas.
3
Registrar en pipeline_runner Agregar la clase a ADAPTERS_DISPONIBLES en core/pipeline_runner.py con la misma clave que usará tenants/{id}.json → erp.tipo.
4
Escribir tests Agregar TestNombreAdapter en tests/test_adapters.py con al menos test_productos_estructura, test_stock_estructura, test_conexion_ok.
5
Validar conexión Antes del pipeline completo, confirmar que test_conexion() retorna True contra el ERP real del cliente piloto.

from core.erp_adapter import ERPAdapter, Producto, Stock, Venta, Pedido

class MiERPAdapter(ERPAdapter):

    def __init__(self, config: dict):
        self._host = config["host"]
        self._user = config["usuario"]
        # descifrar password_enc aquí si aplica

    def test_conexion(self) -> bool:
        try:
            # intento mínimo contra el ERP
            return True
        except Exception:
            return False

    def get_productos(self) -> list[Producto]:
        raw = self._llamar_erp()
        return [
            Producto(codigo=r["id"], descripcion=r["nombre"],
                     marca=r.get("marca"), precio=float(r["precio"]),
                     activo=r.get("activo", True))
            for r in raw
        ]

    def get_stock(self) -> list[Stock]: ...
    def get_ventas(self, desde: str, hasta: str) -> list[Venta]: ...
    def get_pedidos(self) -> list[Pedido]: ...
⚡ Un adapter nuevo nunca debe tocar core/ ni los paneles. Si necesita lógica compartida, agregarla a core/erp_adapter.py como método de clase base — nunca inline en el adapter.

Contrato JSON — Estructura general

Los paneles y cualquier consumidor externo leen exclusivamente estos archivos. Nunca consultan el ERP directamente.

Envelope estándar ("wrapped")

Todos los archivos salvo stock_por_codigo.json usan este wrapper:

{
  "generado":  "2026-07-05T14:30:00+00:00",  // ISO 8601 UTC
  "fuente":    "bsale",                        // clave del ERP origen
  "total":     1240,                           // cantidad de registros
  "registros": [ ... ]                         // array de entidades
}

Reglas para consumidores

  1. Nunca asumir campos adicionales — leer solo los documentados en el contrato.
  2. Verificar total > 0 antes de renderizar cualquier lista.
  3. Usar generado para mostrar cuándo fue la última sincronización.
  4. stock_por_codigo.json es el archivo correcto para buscar stock de un código específico; stock.json para listados y stock multi-bodega.
  5. ventas.json tiene rango acotado — verificar fecha_desde y fecha_hasta antes de mostrar totales históricos.

ERPAdapter API

Clase abstracta base en core/erp_adapter.py. Todos los adapters deben heredar de ella e implementar los 5 métodos.

class ERPAdapter(ABC):

    @abstractmethod
    def test_conexion(self) -> bool:
        """Verifica acceso al ERP. True = OK, False o excepción = fallo."""

    @abstractmethod
    def get_productos(self) -> list[Producto]:
        """Catálogo completo de productos/variantes activos."""

    @abstractmethod
    def get_stock(self) -> list[Stock]:
        """Stock actual por variante y bodega."""

    @abstractmethod
    def get_ventas(self, desde: str, hasta: str) -> list[Venta]:
        """Ventas en el rango [desde, hasta] en formato YYYY-MM-DD."""

    @abstractmethod
    def get_pedidos(self) -> list[Pedido]:
        """Pedidos de compra pendientes o recientes."""

json_writer helpers

from core.json_writer import escribir_wrapped, escribir_raw_dict

# Escribe el envelope estándar
escribir_wrapped(
    ruta    = "data/tenant_x/productos.json",
    registros = [dataclasses.asdict(p) for p in productos],
    fuente  = "bsale",
    extra   = {}          # campos adicionales al wrapper (ej. fecha_desde)
)

# Escribe un dict plano, sin envelope
escribir_raw_dict(
    ruta  = "data/tenant_x/stock_por_codigo.json",
    datos = { s.codigo: {"bodega": s.bodega, "cantidad": s.cantidad} for s in stock }
)
ℹ️ El validator integrado (core/validator.py) corre automáticamente después de cada escritura y lanza ValueError si el JSON no cumple el contrato. El pipeline lo captura y registra en el log de errores del tenant.
